# Publication and PR updates

Follow [Forge policy](../../../docs/policy.md#publication-and-existing-prs) for checkout, plan approval, mode-specific review and publication gates. Complete [Forge's required workflow](../SKILL.md#required-workflow) before submission.

1. Inspect the intended branch, parent and complete task diff. Use [quick-ship](../../quick-ship/SKILL.md) for initial publication authorized directly or through [full-send](../../full-send/SKILL.md) and [graphite](../../graphite/SKILL.md) for stack operations in repositories that use it. Existing open-PR updates follow the canonical policy above.
2. In Graphite repositories inspect the actual stack and dry-run submission. Inspect the intended remote base and commit range as well as the dry run: `--update-only` prevents new PR objects, not exposure of ancestor commits in a child push. If updating the PR would publish an unpublished ancestor or unrelated descendant, keep the validated fix committed locally, name the affected layer and request first-publication authorization. Do not reparent to bypass that gate. Revalidate descendants affected by changed parent behavior. Follow the repository's checks and the graphite/quick-ship command contracts.
3. Write reviewer-facing titles and descriptions under [PR descriptions](../references/pr-descriptions.md), using the repository template and actual ticket conventions. When the repository has no PR template, use [the bundled PR template](../../../templates/pull_request_template.md). Explain behavior, purpose and useful verification; omit process noise and AI signatures. Follow the adopter's PR-interaction rules and authorization.
4. Verify each affected PR's actual head and base and report pending checks honestly. In T3, follow the [host PR lifecycle](../../../docs/harness/t3.md#pr-lifecycle). Outside T3, use the host's native monitor when requested or required.
